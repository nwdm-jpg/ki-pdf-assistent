# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**Clevoriq** ("Dokumente verstehen. Entscheidungen vereinfachen.") is a German-language, AI-powered multi-format document platform — not a "PDF assistant"; PDF is one of several supported formats and should only be named when the PDF format specifically is meant. Clevoriq is the central platform/company brand; the application in this repo is **Clevoriq Documents**, the first (currently only) product on that platform (see "Clevoriq Account, Hub & Products" below) — further Clevoriq products may follow later. After logging in, a user lands in the **Clevoriq Hub** (`hub.py`) — "Meine Produkte", the shared **Clevoriq Library**, and "Konto & Sicherheit" — and opens Clevoriq Documents from there. Inside Clevoriq Documents, users build a persistent, multi-format **document library**, then use it across three AI features — a multi-chat **Chat** assistant, one-off **Analyse & Vergleich** (summarize/compare/deadlines/risks), and a category-based **Dokument prüfen** (document check). Retrieval is semantic (OpenAI embeddings + cosine similarity, with a small keyword bonus), not plain keyword overlap. A separate, much simpler CLI (`app.py`) still exists for a single PDF and has not been migrated to any of this — it keeps its original keyword-overlap retrieval, single-question, no-history behavior, and PDF-only scope by design. The project's repo/folder name (`ki-pdf-assistent`) predates the Clevoriq rebrand (originally "AVENLOQ", rebranded again to Clevoriq) and is not itself user-facing. There is no backend framework and, in active use, no external database (SQLite + local files remain the only backends actually exercised — PostgreSQL/S3 support is prepared but not yet portable/active, see "Data & Storage Backends") — this is a small, personal project — though `test_auth_security.py`/`test_hub_produkte.py`/`test_storage_db_backend.py` do cover the Streamlit-independent modules (see "Testing approach").

Supported document formats: **PDF, DOCX, TXT, MD, CSV, XLSX, PPTX** (see `dokument_verarbeitung.SUPPORTED_EXTENSIONS`).

## Commands

`requirements.txt` lists runtime dependencies (`streamlit`, `openai`, `pypdf`, `numpy`, `python-docx`, `openpyxl`, `python-pptx`); there is no `pyproject.toml`. Install into the existing `.venv`.

```bash
# Activate the existing venv (Windows)
.venv\Scripts\activate

# Install dependencies
pip install -r requirements.txt

# Run the Streamlit web app (primary entry point: library, chats, analysis, document check)
streamlit run web_app.py

# Run the legacy CLI version (single PDF from pdfs/, keyword retrieval, no history)
python app.py

# Sanity-check the OpenAI API connection/credentials
python api_test.py
```

An `OPENAI_API_KEY` must be available in the environment (the `openai.OpenAI()` client picks it up automatically) for any of the above to work.

There are no lint, format, or test commands configured in this repo.

## Architecture

### Module/file structure

- **`web_app.py`** — Streamlit UI, the main entry point. Areas are selected via `st.session_state.aktiver_bereich` (a plain session variable, not a widget-bound key, so both the sidebar nav and the various cards can set it): 🏠 Clevoriq Hub, 🏠 Startseite (Documents home), 💬 Chat, 🔍 Analyse & Vergleich, 🛡️ Dokument prüfen, 📚 Dokumentenbibliothek (shared, see below), plus Konto & Sicherheit/Verifizierung. A second, parallel piece of state, `st.session_state.aktiver_kontext` (`"hub"` or `"documents"`), decides which nav *group* the sidebar shows — see "Clevoriq Account, Hub & Products" below. Owns the single upload/processing path (`dateien_verarbeiten`), the server-side product-access gate (`DOCUMENTS_BEREICHE` check, enforced on every script run, not just a hidden button), and all Streamlit widget/spinner/error-boundary orchestration.
- **`hub.py`** — Streamlit UI for the Clevoriq Hub (`BEREICH_HUB`, the post-login landing page): renders "Meine Produkte" (one card per `produkte.PRODUKTE` entry, status driven by `speicher.produkt_zugriff_aktiv`, plus a static neutral "Weitere Produkte — Demnächst verfügbar" card) and quick-access cards into the shared Library and Konto & Sicherheit. Contains no navigation/session logic itself — `seite()` only returns which `AKTION_*` the user clicked in this run; `web_app.py` performs the actual bereich/kontext switch and re-checks product access server-side before doing so.
- **`produkte.py`** — pure, data-driven product registry: `PRODUKTE` (product_key → name/icon/description) and `PRODUKT_DOCUMENTS = "documents"`. Contains no access-control logic (that's `speicher.produkt_zugriffe`, see "Persistent storage") and no Streamlit — a future second product is a new dict entry here plus grant calls, never a new if/else special case anywhere else.
- **`bibliothek_ansicht.py`** — the ONE Streamlit rendering implementation of the "Clevoriq Library" (`rendern(benutzer_id, dateien_verarbeiten)`): upload, search/filter/sort, rename, delete. Called identically from both the Hub's "Zentrale Bibliothek" entry and Clevoriq Documents' "Dokumentenbibliothek" entry — see "Clevoriq Account, Hub & Products" below for why this guarantees the two are always in sync without any explicit synchronization step.
- **`app.py`** — legacy CLI for a *single* PDF: loads a file by filename from `pdfs/`, loops on stdin questions until `ende`. Independent, unmigrated code path — no multi-document, no library, no semantic search, no chat history.
- **`pdf_logik.py`** — owns the module-level OpenAI `client` and `MODELL` (`"gpt-5-mini"`, `client.responses.create`, Responses API) that every other module imports rather than creating its own client. Otherwise holds only the legacy, PDF-only, keyword-overlap pipeline used exclusively by `app.py` (`pdf_seiten_extrahieren`, `relevante_seiten_ermitteln`, `relevanten_text_zusammenstellen`, `verwendete_quellen`, `formatiere_quellenhinweis`, `frage_beantworten`). `web_app.py` imports only `frage_beantworten` from here for the Chat area's final answer call; everything else in the multi-document path uses `quellen.py` / `retrieval.py` / `ki_analyse.py` instead of this module's equivalents.
- **`dokument_verarbeitung.py`** — format-detecting document parser. Supports PDF, DOCX, TXT, MD, CSV, XLSX, PPTX (`SUPPORTED_EXTENSIONS`, `PARSER_JE_ENDUNG`). Each format has a small `_..._einheiten` parser that splits a file into "Einheiten" (page/slide/sheet/section — one logical unit each); all parsers feed into the shared `text_in_chunks_aufteilen` (sentence-aware, ~1000 chars, 150-char overlap). Adding a new format means writing one parser function and a `PARSER_JE_ENDUNG` entry — the rest of the pipeline (chunking, storage, retrieval, source formatting) is unchanged. Unsupported extensions raise `NichtUnterstuetzterDateityp` with a clear German message instead of crashing.
- **`retrieval.py`** — semantic search over stored chunks using OpenAI embeddings (`text-embedding-3-small`). Score = cosine similarity (primary) + a small (0.15) keyword-overlap bonus, so exact term matches aren't lost to pure embedding similarity. Selects the top N chunks **per document**, never a single global top-N — this guarantees every active document stays visible to the model even when chat-history context (`zusatzkontext`) biases the query toward one document. `embeddings_batch_erstellen` embeds a whole document's chunks in one API call.
- **`speicher.py`** — the Clevoriq Library Service / data-access layer: SQLite metadata + (via `storage.py`) file persistence, all under project-local `app_daten/` (gitignored) for the `local`/`sqlite` backends. See "Persistent storage" below and "Data & Storage Backends" further below for the DB/object-storage abstraction this sits on.
- **`db_backend.py`** — dual-backend database abstraction (`sqlite`/`postgresql`, via `CLEVORIQ_DATABASE_BACKEND`): connection setup, a portable connection/cursor wrapper (`?`→`%s` translation, dict rows, `rowcount`), and the handful of genuinely dialect-specific helpers (`insert_und_id_zurueckgeben`, `upsert_ignore`, `upsert_ersetzen`, `spalten_vorhanden`). `speicher._verbindung()` delegates here; `speicher.py`'s SQL text itself is dialect-agnostic. See "Data & Storage Backends" below.
- **`storage.py`** — file *storage* abstraction (`local`/`s3`, via `CLEVORIQ_STORAGE_BACKEND`): `LocalFileStorage` (today's backend) and `S3Storage` (prepared for IONOS Object Storage, S3-compatible). `speicher.py` is the only caller. See "Data & Storage Backends" below.
- **`quellen.py`** — the one source-formatting/prompt-text-assembly implementation for the multi-format path (Chat, Analyse & Vergleich, Dokument prüfen): `relevanten_text_zusammenstellen`, `verwendete_quellen`, `formatiere_quellenhinweis`. Format-aware (Seite/Folie/Tabellenblatt/Abschnitt via `EINHEIT_WOERTER`) and backward-compatible with legacy 2-tuple `(dateiname, seitennummer)` sources stored in old chat messages, so no data migration was needed when this replaced the equivalent functions in `pdf_logik.py` for everything except `app.py`.
- **`ki_analyse.py`** — shared retrieval/prompt/API plumbing used by both `analyse.py` and `pruefung.py`, so that logic isn't duplicated between the two features: `ausschnitte_ermitteln` (load a document selection's chunks, semantic-select the best), `ki_anfrage` (assemble system/history/content messages, call the Responses API, return `{text, quellen, quellenhinweis}`), `rueckfrage_beantworten` (generic follow-up-question handler for an already-produced result, parameterized by `kontext_label` so callers keep independent follow-up threads). Also defines the shared `KUERZE_HINWEIS` (terseness instruction) and `QUELLENFORMAT_HINWEIS` (in-text citation format instruction) used by every AI-analysis system prompt.
- **`analyse.py`** — Analyse & Vergleich feature: `zusammenfassen`, `vergleichen`, `fristen_ermitteln`, `risiken_ermitteln`. Each is a fixed topical search query (there's no user question to search on) + a dedicated system prompt, built on `ki_analyse.py`. `rueckfrage_beantworten` wraps `ki_analyse.rueckfrage_beantworten` with `kontext_label="Analyseergebnis"`.
- **`pruefung.py`** — Dokument prüfen feature: data-driven `KATEGORIEN` (risiken, kosten, fristen, pflichten_eigene, pflichten_gegenseite, unklare_regelungen — each icon/title/focus/search-query) and `PRESETS` (allgemein/vertrag/angebot/rechnung — a title + extra focus clause). Adding a category or preset is a new dict entry only. `einzelpruefung` runs one category; `kompletter_check` runs all categories through **one** combined search query + **one** model call (see cost-awareness below). Priority markers 🔴/🟡/🟢 are enforced via `_PRIORITAETS_ANWEISUNG`. `rueckfrage_beantworten` wraps `ki_analyse.rueckfrage_beantworten` with `kontext_label="Prüfungsergebnis"`.
- **`dokumentbibliothek.py`** — pure, Streamlit-independent filter/sort/display helpers for the library view (`dokumente_filtern`, `dokumente_sortieren`, `dateityp_anzeige`, `einheiten_text`, `groesse_text`, date-range constants), used by `bibliothek_ansicht.py`. Never mutates the documents passed in or any selection/session state — search/sort/filter are purely presentational.
- **`komponenten.py`** — shared Streamlit UI building blocks reused across areas: `nav_eintrag`/`start_karte`/`modus_karte` (navigation and action cards), `dokument_mehrfachauswahl` (multi-select with session-state persistence that survives a run where the widget isn't drawn), `ergebnis_kopf` + `rueckfragen_chat` (result header and generic follow-up chat UI shared by Analyse & Vergleich and Dokument prüfen), `quellen_hinweis`, `seiten_kopf`, `leerer_zustand`, `marke_kopf`/`marke_tagline`/`hero_glow` (Clevoriq wordmark/tagline/hero glow), `hinweis_dezent` (subdued disclaimer notice). Base colors/radii come from the native Streamlit theme (`.streamlit/config.toml`); `css_einbinden` layers the one centralized brand CSS block (design tokens, gradient, wordmark, Inter font, button-hierarchy/danger styling, card system, animated mesh background, structural tweaks like card min-height) on top — see "Brand & Design System" above.
- **`api_test.py`** — minimal standalone script to verify the OpenAI API key/connection works.

### Data model

Two related but distinct entry shapes exist side by side:

- **Legacy Seiteneintrag** (`pdf_logik.py`, used only by `app.py`): `{"dateiname": str, "seitennummer": int, "text": str}` — one page of one PDF.
- **Chunk** (`dokument_verarbeitung.py` onward, used everywhere else): `{"dateiname": str, "seitennummer": int, "einheit_typ": str, "einheit_anzeige": str, "text": str}`, plus `"embedding"` once loaded from/written to storage. `einheit_typ` is one of `seite`/`folie`/`tabellenblatt`/`abschnitt` (see `quellen.EINHEIT_WOERTER`); `einheit_anzeige` is the human-facing label (e.g. a sheet name). `quellen.py` also transparently accepts legacy 2-tuple `(dateiname, seitennummer)` sources, so old stored chat messages keep rendering correctly.

### Persistent storage

Everything lives under project-local `app_daten/` (gitignored — never committed):

- `app_daten/bibliothek.db` — SQLite (or, if `CLEVORIQ_DATABASE_BACKEND=postgresql`, the equivalent PostgreSQL database — same schema, see "Data & Storage Backends" below). `dokumente` (id, user_id FK CASCADE, dateiname, hash UNIQUE(hash, user_id), seitenzahl, hochgeladen_am, dateityp, einheit_typ, groesse_bytes, **public_id** — a stable UUID, see "Zentrale Dokument-ID" below, **storage_key** — the opaque, server-generated file location, see "Data & Storage Backends" below) is the central, product-agnostic Library table — Clevoriq Documents-specific data (chunks/embeddings, chat Q&A) lives in separate tables that reference it (see "Clevoriq Account, Hub & Products" below): `chunks` (id, dokument_id FK CASCADE, seitennummer, text, embedding BLOB/BYTEA, einheit_typ, einheit_anzeige), `chats` (id, titel, erstellt_am, aktualisiert_am, dokument_ids JSON list), `nachrichten` (id, chat_id FK CASCADE, frage, antwort, quellen JSON, erstellt_am). `produkt_zugriffe` (id, user_id FK CASCADE, product_key, status, plan, aktiviert_am, laeuft_ab_am, UNIQUE(user_id, product_key)) is the product-permission table — see "Clevoriq Account, Hub & Products" below. `storage_cleanup_auftraege` is the storage-delete outbox — see "Data & Storage Backends" below.
- `app_daten/users/<user_id>/documents/...` — original uploaded file bytes, under the `local` storage backend's basis folder (`storage.LocalFileStorage(speicher.APP_DATEN_ORDNER)`). New documents get a `storage_key` of the form `users/<user_id>/documents/<public_id>/original.<extension>` (`speicher.dokument_speichern`); pre-existing documents keep their historical `users/<user_id>/documents/<sha256-hash>.<extension>` location, backfilled into `storage_key` as-is (`speicher._dokumente_storage_keys_ergaenzen`, additive, no file ever moved). The hash still drives upload dedup (`speicher.dokument_nach_hash`) — re-uploading identical bytes is a no-op — independent of where/how the file is physically stored.
- Schema changes are additive-only and dialect-agnostic: `speicher._spalten_ergaenzen` uses `db_backend.spalten_vorhanden` (`PRAGMA table_info` under SQLite, `information_schema.columns` under PostgreSQL) and runs `ALTER TABLE ... ADD COLUMN` for anything missing, on every startup. There is no migration framework and no destructive schema change should be introduced without discussing it first — existing rows/databases must keep working, on both backends.
- Deleting a document (`speicher.dokument_loeschen`) cascades chunk deletion via FK, actively strips that document's id from every chat's `dokument_ids`, and deletes its file copy via the storage layer — through the storage-cleanup outbox (see "Data & Storage Backends" below), never a direct, un-recoverable filesystem call.
- The project-root `pdfs/` folder is unrelated to any of this — it's `app.py`'s original CLI-only sample folder. (The historical `app_daten/pdfs/` folder from before the multi-user upgrade is migrated away entirely by `speicher._dateien_migrieren`, unrelated to `storage_key`.)

### Multi-format document support

`dokument_verarbeitung.py` supports PDF, DOCX, TXT, MD, CSV, XLSX, PPTX. Each format parses into "Einheiten" — pages (PDF), slides (PPTX), sheets (XLSX, capped at 500 rows/sheet), or size-targeted paragraph sections (~1500 chars — DOCX/TXT/MD via `_absaetze_zu_abschnitten`, CSV in 50-row blocks) — which then all go through the same `text_in_chunks_aufteilen`. This is the only chunking implementation in the app.

### Document library workspace

📚 Dokumentenbibliothek — rendered by `bibliothek_ansicht.rendern`, reachable from both the Clevoriq Hub and from within Clevoriq Documents (see "Clevoriq Account, Hub & Products" below) — is the single place documents are uploaded and processed (`web_app.py`'s `dateien_verarbeiten`, passed in as a callback); Chat, Analyse & Vergleich, and Dokument prüfen all read from this shared library rather than re-uploading. The library view adds search, file-type filter, upload-date filter, eight sort orders, and renaming (`speicher.dokument_umbenennen`), all via the pure functions in `dokumentbibliothek.py` plus `speicher.py` — filtering/sorting never touches selection state in any of the feature areas.

### Semantic retrieval

`retrieval.py` (embeddings + cosine similarity + keyword bonus, per-document top-N) is used everywhere in the multi-document path — Chat, Analyse & Vergleich (via `ki_analyse.ausschnitte_ermitteln`), Dokument prüfen (same). It supersedes, but does not remove, the plain keyword-overlap retrieval in `pdf_logik.py`, which remains exclusively `app.py`'s (unmigrated) retrieval method.

### Generic source formatting

`quellen.py` is format-aware: it renders `"Seite 3"`, `"Folie 7"`, `"Tabellenblatt \"Kosten\""`, `"Abschnitt 2"` etc. depending on `einheit_typ`, groups by filename (and by unit-type within a filename if a document mixes types), sorts numeric display values ascending and non-numeric ones alphabetically-quoted, and dedups. It replaces `pdf_logik.formatiere_quellenhinweis`/`verwendete_quellen`/`relevanten_text_zusammenstellen` for every caller except `app.py`.

### Multiple chats

`speicher.py`'s `chats`/`nachrichten` tables back a full multi-chat sidebar: create (`chat_erstellen`), list (`chat_liste`, most-recently-updated first), switch, delete (`chat_loeschen`, with fallback to a fresh chat if the active one is deleted). A chat's title is auto-derived from its first question via a plain string heuristic (`_kurztitel_erzeugen`, ≤45 chars) — deliberately *not* a model call, to avoid spending API cost on titling.

### Per-chat document selections

`chats.dokument_ids` (JSON) holds each chat's own active-document set, independent of the Analyse & Vergleich and Dokument prüfen selections. The sidebar's multiselect (visible only while the Chat area is active) uses a per-chat session-state key (`chat_dokument_ids_{chat_id}`) via `komponenten.dokument_mehrfachauswahl`, so switching chats mid-session never bleeds one chat's selection into another's. Only a chat's active documents feed its retrieval and answers; deleted documents are silently dropped from `dokument_ids` on load (`speicher._existierende_dokument_ids`).

### Analyse & Vergleich (`analyse.py`, `web_app.py` BEREICH_ANALYSE)

Four fixed actions over an independently-selected multi-document set (own `session_key`, unrelated to Chat's or Dokument prüfen's): Zusammenfassen (≥1 doc), Dokumente vergleichen (≥2 docs), Fristen & Termine, Risiken & Auffälligkeiten. Each runs a fixed topical search query (no user question exists to search on) through `ki_analyse`, then renders the structured result plus a dedicated follow-up (`rueckfragen`) chat thread held in `st.session_state.analyse_ergebnis`.

### Dokument prüfen (`pruefung.py`, `web_app.py` BEREICH_PRUEFUNG)

Six categories × four presets, both fully data-driven (`KATEGORIEN`, `PRESETS`) so new ones need no UI or control-flow changes. A user can run one category (`einzelpruefung`) or the full check (`kompletter_check` — all categories, one combined query, one model call). Each result gets a priority-annotated (🔴/🟡/🟢) breakdown and its own follow-up chat thread, independent of Analyse & Vergleich's and Chat's, and its own document selection.

### Shared analysis/retrieval helpers (`ki_analyse.py`)

The retrieval → prompt-assembly → Responses-API-call → source-formatting pipeline used by both `analyse.py` and `pruefung.py` lives here exactly once, along with the two shared system-prompt fragments (`KUERZE_HINWEIS`, `QUELLENFORMAT_HINWEIS`) that keep every AI-analysis feature's output equally terse and equally well-sourced. New AI-analysis features (beyond Analyse & Vergleich / Dokument prüfen) should be built on this module rather than re-implementing retrieval or prompt assembly.

### Language convention

All UI strings, variable/function names, and prompts are in German (e.g. `frage` = question, `antwort` = answer, `seiten` = pages, `dokumente` = documents, `bewertete_seiten` = scored pages). Keep new code consistent with this convention.

## Brand & Design System

Clevoriq's identity is: modern, professional, trustworthy, intelligent, clean, premium SaaS — not playful, not futuristic. The visual direction is **white-first**: a bright, clean, professional content area with a blue+red accent system, dynamic gradients, and subtle motion, layered on top rather than replacing the neutral base. Preserve these when touching UI:

- **Palette**: white-first content area (`#FFFFFF` primary surface, `#F8FAFC`/`#F1F5F9` light background tints), dark Navy `#0B1120` sidebar, Primary Blue `#2563EB`, Violet `#7C3AED` (gradient midpoint only), strong Red `#E53935`, dark ink/text `#111827`. Base theme (light content + dark navy sidebar) lives in `.streamlit/config.toml` (`[theme]` + `[theme.sidebar]`); all brand design tokens (colors, gradients, shadows, radii, animation timing — `--clv-*` custom properties) and everything the native theme can't express live in the single centralized CSS block in `komponenten.py` (`_CSS`) — don't scatter new CSS/`st.html` styling into `web_app.py`.
- **Gradient discipline**: the blue→violet→red gradient (`--clv-gradient`) is reserved for primary actions, active/selected navigation, the wordmark, the Startseite tagline, and the Startseite hero glow — driven by `button[kind="primary"]` CSS plus `komponenten.marke_kopf`/`marke_tagline`/`hero_glow`. Blue and red are used *deliberately* as accents (card hover glows, danger actions, small highlights); ordinary UI (secondary buttons, card surfaces, inputs) stays white/neutral — don't make the whole app colorful.
- **Button hierarchy**: primary (`type="primary"`) = gradient with a subtle hover lift/glow, for the one main action per view; secondary (`type="secondary"`, the default) = white/neutral with a hairline border in the main content area, dark ghost style in the sidebar (see `[data-testid="stMain"] button[kind="secondary"]` vs. `[data-testid="stSidebar"] button[kind="secondary"]` in `_CSS`); danger = the destructive "Endgültig löschen" pattern only, styled red via the `[class*="st-key-bibliothek_confirm_del_"]` CSS hook in `komponenten.py` — follow the same key-prefix pattern for any new destructive-confirmation button rather than reusing `type="primary"`. All hover transitions use `--clv-transition` (~200ms) — keep motion subtle, no large/bouncy animations.
- **Cards**: every bordered `st.container(border=True)` in the main content area (Startseite, Dokumentenbibliothek, Analyse & Vergleich, Dokument prüfen, Konto & Sicherheit, Login/Register) shares one card system via the generic `[data-testid="stVerticalBlockBorderWrapper"]` rule in `_CSS`: white surface (native theme), `--clv-radius` (18px) corners, a soft resting shadow, a gentle fade-in on appearance, and a hover lift with a slightly stronger shadow (plus an alternating blue/red border tint on the four Startseite action cards). Don't add one-off card styling per page — extend the shared rule instead.
- **Dynamic background**: `[data-testid="stMain"]::before` renders a very low-opacity, slow-drifting blue/violet/red mesh-gradient behind all main-area content (never the sidebar); `komponenten.hero_glow()` adds a stronger but still subtle animated glow behind the Startseite hero specifically. Both respect `prefers-reduced-motion` (animation is disabled entirely when the user prefers reduced motion) and are simplified/disabled on narrow viewports for performance. Never raise opacity to the point of hurting text contrast.
- **Wordmark**: `komponenten.marke_kopf(gross=False, produkt=komponenten.PRODUKT_NAME)` renders the icon+"Clevoriq" lockup with the current product name ("Documents") stacked smaller/subtler beneath it; `gross=True` is the larger Startseite/Login-hero variant; `produkt=None` omits the product line. See "Platform & Product Branding" below for the Clevoriq-vs-product hierarchy this exists to support. The icon is a pure CSS/text mark (`.avq-marke-icon` gradient tile + "C") rather than an inlined SVG — `st.html` runs its content through DOMPurify, which strips `<svg>` content, so an inline SVG icon renders invisible. `assets/logo.svg` / `assets/logo_icon.svg` remain as prepared, self-authored source assets for a future real logo (e.g. a rasterized favicon or an `st.image`-based swap); update `marke_kopf` to use them once a non-SVG asset (or a sanitizer-safe embedding method) is available, without changing call sites. CSS class names keep the historical `avq-` prefix (an internal implementation detail, not user-facing) to keep the rebrand diff small. Never use an emoji as the product logo (emojis remain fine for nav/card icons, e.g. 💬🔍🛡️📚).
- **Typography**: Inter (loaded via Google Fonts `@import` in `komponenten.py`'s CSS, with a system sans-serif fallback), applied globally; avoid decorative fonts or oversized text outside the Startseite hero.
- **Disclaimers**: legal/analysis disclaimers (`analyse.RISIKEN_HINWEIS`, `pruefung.PRUEFUNG_HINWEIS`) render via `komponenten.hinweis_dezent`, a subdued blue-accent notice — not `st.warning` — to stay professional rather than alarming. Never add "100% secure" / "DSGVO-konform" / "rechtssicher" style claims; even with the auth/session/rate-limiting hardening described in "Authentication & Security" below, hosting and a final, professionally reviewed privacy/security architecture don't exist yet.
- **Wording**: refer to the product as "Clevoriq" (or "Clevoriq Documents" where the product specifically, not just the account/platform, is meant), never "AVENLOQ"/"KI-PDF-Assistent"/"PDF-Assistent". Prefer format-neutral wording ("Dokument", "Datei") in product-facing UI text; keep "PDF" only where the PDF format specifically is meant (`app.py`, `dokument_verarbeitung.py`, `speicher.py`'s `PDF_ORDNER`, format badges, etc. — these are correct as-is, not leftover branding).

## Platform & Product Branding

Clevoriq is the central platform/company brand; the account is a Clevoriq account, not tied to one product. The application in this repo is **Clevoriq Documents**, the first (currently only) product on that platform. Visual hierarchy is always Clevoriq dominant, product name smaller/subtler beneath it (`komponenten.marke_kopf`'s `produkt` parameter, default `komponenten.PRODUKT_NAME = "Documents"`, rendered via `.avq-marke-produkt` in `_CSS`) — never the other way round, and never two products shown at once.

The Clevoriq account (`benutzer.py`/`speicher.py`) is intended to eventually be shared across future Clevoriq products. Cross-product single sign-on is **not implemented** — sessions are per-app `st.session_state` only (see `benutzer.py`'s module docstring). Do not build SSO, a product switcher, additional products, or placeholders for them unless explicitly requested; `marke_kopf`'s `produkt` parameter exists solely so a future product can reuse the same wordmark component without changing this one, not as an invitation to add one now.

## Clevoriq Account, Hub & Products

This section documents the target architecture introduced to prepare (without yet building) a real multi-product Clevoriq platform:

```
Clevoriq Account
      ↓
Clevoriq Hub                (hub.py, BEREICH_HUB — post-login landing page)
      ↓
┌─────────────────────────┐
│ Meine Produkte          │  → produkte.py + speicher.produkt_zugriffe
│ Zentrale Bibliothek     │  → bibliothek_ansicht.py + speicher.py's dokument_*/chunks_* functions
│ Konto & Sicherheit      │  → konto.py (unchanged)
└─────────────────────────┘
      ↓ ("Öffnen", server-side product-access check)
Clevoriq Documents          (BEREICH_START/CHAT/ANALYSE/PRUEFUNG/BIBLIOTHEK)
```

- **One account, not one account per product.** The existing login/registration/verification/reset/session/2FA stack (see "Authentication & Security" below) *is* the Clevoriq Account — nothing about it changed in this block. A verified login now lands in the Clevoriq Hub (`BEREICH_HUB`) instead of directly in Clevoriq Documents; an unverified account is still routed exclusively to `BEREICH_VERIFIZIERUNG`/`BEREICH_KONTO`, unchanged.
- **Hub ↔ Documents is a context switch inside one session, never a second login.** `web_app.py` tracks `st.session_state.aktiver_kontext` (`"hub"` / `"documents"`) alongside `aktiver_bereich`; clicking "Öffnen" on the Documents card only flips this in-memory context and re-uses the existing `sessions` row (`speicher.sitzung_erstellen` is *not* called again) — see "Session model" below. "← Zurück zum Clevoriq Hub" flips it back. Shared areas (Bibliothek, Konto & Sicherheit) don't change the context, so returning to the previous nav group afterwards makes sense.
- **Product access is a data-driven permission table, not a code special-case.** `speicher.produkt_zugriffe` (user_id, product_key, status, plan, aktiviert_am, laeuft_ab_am) answers "which products does this user own, on what plan, since when, active or locked/deactivated" — see "Persistent storage" above for the schema. `produkte.py` holds only the *registry* of technically-existing products (name/icon/description per `product_key`), never an access decision. Today only `produkte.PRODUKT_DOCUMENTS = "documents"` is real; both new registrations (`speicher.benutzer_erstellen`) and pre-existing accounts (`speicher._produktzugriffe_migrieren`, additive migration, runs every startup) are automatically granted active Documents access — there is still no purchase/subscription flow. A future second product needs only a new `produkte.PRODUKTE` entry plus `speicher.produkt_zugriff_gewaehren` calls — never a new `if user == ...`-style special case. The Hub's "Meine Produkte" therefore shows one card per registry entry (status from `speicher.produkt_zugriff_aktiv`) plus a static, neutral "Weitere Produkte — Demnächst verfügbar" card (no invented future product names).
- **Deny by default, enforced server-side, not just a hidden button.** `web_app.py` checks `speicher.produkt_zugriff_aktiv(benutzer_id, produkte.PRODUKT_DOCUMENTS)` on *every* script run before rendering any of `DOCUMENTS_BEREICHE` (Startseite/Chat/Analyse/Prüfung) — a locked/expired product access forces `aktiver_bereich` back to `BEREICH_HUB` regardless of how it was set, not merely a disabled "Öffnen" button in `hub.py` (which exists too, but is cosmetic only, same philosophy as the existing 2FA UI-gating — see "Session model" below).
- **One central Library, no Hub-vs-Documents duplication.** There is exactly one Streamlit rendering function for the library view, `bibliothek_ansicht.rendern(benutzer_id, dateien_verarbeiten)`, called identically from the Hub's "Zentrale Bibliothek" nav entry and from Clevoriq Documents' "Dokumentenbibliothek" nav entry. Both calls query the exact same `speicher.py` functions (`dokumente_laden`, `dokument_speichern`, `dokument_umbenennen`, `dokument_loeschen`) against the exact same SQLite table on every script run — Streamlit re-executes the whole script on every interaction and nothing here is cached (`st.cache_data`/`st.cache_resource` are not used on these functions), so an upload/rename/delete performed from one entry point is visible from the other on the very next rerun. There is no sync job and no copy to keep in sync because there was never a second copy to begin with.
- **Central file/metadata vs. product-specific data stays separated, as it already was.** `dokumente` (filename, owner, file type, upload date, shared metadata, `public_id`) is the central Library record; `chunks`/`chats`/`nachrichten` (embeddings, chat Q&A, analysis) are Clevoriq Documents-specific and merely reference `dokumente.id` by foreign key — this split already existed before this block (see "Data model"/"Persistent storage" above) and is preserved, not newly introduced. A future second product would get its own product-specific tables referencing `dokumente.id` the same way, never new columns bolted onto `dokumente` itself.
- **Zentrale Dokument-ID.** `dokumente.public_id` is a UUID4 assigned at creation (`dokument_speichern`) and idempotently backfilled for pre-existing rows on every startup (`speicher._dokumente_public_ids_ergaenzen`, additive, stable — a value, once assigned, never changes on a later run). It exists to let a future second product or a future API reference a document without leaking the internal, sequential `id`. **It is never itself an access credential**: `speicher.dokument_nach_public_id(public_id, benutzer_id)` — like every other document-accessing function in `speicher.py` — filters by `user_id` in the same query, so knowing another user's `public_id` (exactly like knowing their internal `id`) grants no access whatsoever.
- **Ownership stays user-based; Teams/Organizations are explicitly out of scope for now.** Every document/chat is still owned by exactly one `user_id`, unchanged. No org/team/invitation/role tables exist yet — nothing in this block should be read as a step toward inventing them prematurely, but nothing here (per-user `produkt_zugriffe` rows, per-user document ownership) blocks adding a `team_id` layer later.
- **Still no real SSO/OIDC, no self-built JWTs, no cross-subdomain cookies.** The Hub→Documents transition is a same-`st.session_state` context flip, not a protocol — see "Session model" below for the underlying, unchanged single-session-token model and its known Streamlit limitations (no HttpOnly/Secure cookie, no browser-level binding). When Clevoriq products eventually become separate deployed services, that transition needs a real, standards-based SSO/OIDC flow between them — do not attempt to simulate that with homegrown tokens or cookies in the meantime.
- **`speicher.py` is the Clevoriq Library Service.** Every document read/write goes through owner-checked functions here (`dokumente_laden`, `dokument_speichern`, `dokument_loeschen`, `chunks_laden`, `dokument_umbenennen`, `dokument_nach_public_id`, ...). No UI module builds its own SQL or touches a file path directly. This is what makes the DB/storage backend swap described in "Data & Storage Backends" below possible *underneath* this same layer rather than a rewrite of every caller.
- **No purchase/subscription flow.** `produkt_zugriffe.plan`/`status`/`laeuft_ab_am` are schema-ready for a future paid plan (e.g. a cron job or webhook setting `status = 'gesperrt'`/`laeuft_ab_am`), but nothing in the app currently sets anything other than an immediately-active, unlimited grant — no Stripe/PayPal/IONOS billing integration exists.

## Data & Storage Backends

This section documents the dual-backend data-access architecture — **SQLite stays the active development backend**; **PostgreSQL (target: IONOS Managed PostgreSQL) is now fully schema-/query-compatible but has never been exercised against a real server** — plus the Object Storage abstraction and the storage cleanup outbox. No real cloud infrastructure exists yet.

```
Clevoriq Library Service (speicher.py)
        │
        ├── DB abstraction (db_backend.py)
        │       ├── Connection layer: sqlite_verbindung / postgresql_verbindung
        │       │     (credentials, SSL mode, commit-on-success/rollback-on-error)
        │       ├── _PortableConnection / _PortableCursor
        │       │     (? → %s translation, dict rows on both drivers,
        │       │      rowcount passthrough, executescript)
        │       └── insert_und_id_zurueckgeben / upsert_ignore / upsert_ersetzen /
        │             spalten_vorhanden  (the few genuinely dialect-specific ops)
        │
        └── Storage abstraction (storage.py)
                ├── LocalFileStorage — today's active backend
                └── S3Storage        — S3-compatible (IONOS Object Storage
                                       target), fully implemented, not yet
                                       exercised against real cloud infra
```

### Dual-backend SQL: what's abstracted and how

- **`speicher.py` writes ONE SQL text per query, always with `?` placeholders — never a dialect check in business logic.** `db_backend._PortableConnection.execute/executemany` translates `?` → `%s` automatically when the configured backend is PostgreSQL (pure text substitution on the SQL string — verified that no query anywhere in `speicher.py` has a literal `?` character inside a string constant, so this is unambiguous) and leaves it untouched for SQLite. Bound parameter *values* are never string-interpolated on either path — always passed through the driver's own parameter binding.
- **Rows are always plain `dict`s.** `_PortableCursor.fetchone`/`fetchall` wrap both `sqlite3.Row` and `psycopg2.extras.RealDictRow` results in `dict(...)`, so `zeile["spalte"]` and `dict(zeile)` behave identically regardless of backend — `speicher.py`'s ~150 call sites needed no changes for this.
- **`cursor.lastrowid` is SQLite-only and now confined to `db_backend.insert_und_id_zurueckgeben(conn, sql, params, id_spalte="id")`** — the ONLY four call sites that ever needed a newly-inserted id (`benutzer_erstellen`, `_migrations_benutzer_id`, `dokument_speichern`, `chat_erstellen`) go through this helper: SQLite uses `cursor.lastrowid` directly, PostgreSQL gets ` RETURNING {id_spalte}` appended to the statement and reads the id from the returned row. No `SELECT MAX(id)` workaround anywhere. Accessing `.lastrowid` directly on a PostgreSQL-backed cursor now raises a loud `db_backend.DatenbankFehler` instead of silently doing the wrong thing.
- **`INSERT OR IGNORE` → `db_backend.upsert_ignore(conn, tabelle, spalten, werte, konflikt_spalten)`** (SQLite: `INSERT OR IGNORE`; PostgreSQL: `ON CONFLICT (...) DO NOTHING`) — same fachliche Semantik on both: never overwrites an existing row, whatever its current state. Used by `produkt_zugriff_gewaehren`.
- **A genuine "check-then-insert-or-update" race (`zwei_faktor_setup_starten`) became one atomic `db_backend.upsert_ersetzen(conn, tabelle, konflikt_spalten, spalten_werte)`** (`INSERT ... ON CONFLICT (...) DO UPDATE SET spalte = excluded.spalte, ...` — `EXCLUDED`/`excluded` is one of the rare syntax elements SQLite deliberately copied from PostgreSQL, so this is identical text on both backends) instead of a separate SELECT followed by a Python-side branch.
- **Schema is ONE template, `speicher._SCHEMA_VORLAGE`, instantiated per dialect by `speicher._schema_sql()`.** The only two substitutions: `{PK}` (`INTEGER PRIMARY KEY AUTOINCREMENT` for SQLite vs. `SERIAL PRIMARY KEY` for PostgreSQL — except `zwei_faktor.user_id`, which is deliberately never autoincrementing on either backend, since its value *is* the referenced `benutzer.id`) and `{BLOB}` (`BLOB` vs. `BYTEA`, for `chunks.embedding`). Everything else — `TEXT`/`INTEGER` types, `UNIQUE`, `REFERENCES ... ON DELETE CASCADE`, `CREATE INDEX IF NOT EXISTS`, the partial unique index on `dokumente.public_id` — is identical, portable SQL on both.
- **Additive column migration (`speicher._spalten_ergaenzen`) is dialect-aware via `db_backend.spalten_vorhanden(conn, tabelle)`** (`PRAGMA table_info` under SQLite, `information_schema.columns` under PostgreSQL) — `ALTER TABLE ... ADD COLUMN` itself is identical syntax on both.
- **The three legacy one-off repair migrations stay SQLite-only, by design, and are skipped entirely for PostgreSQL** (`_dokumente_tabelle_neu_aufbauen`/`_chunks_tabelle_neu_aufbauen`/`_chats_tabelle_neu_aufbauen`, still using raw `sqlite3.connect` + `PRAGMA legacy_alter_table`): they repair damage that could only ever occur under SQLite's specific `ALTER TABLE ... RENAME TO` foreign-key-rewriting behavior, on databases that predate the multi-user upgrade. A freshly created PostgreSQL database never passed through that history, so `speicher.datenbank_initialisieren()` guards every call to these three functions (and their SQLite-only detection helpers) behind `not db_backend.ist_postgresql()` rather than porting genuinely SQLite-specific bug-repair logic that a PostgreSQL database structurally cannot need.
- **`SQLite IS NOT <value>` (a SQLite-only extension) → `IS DISTINCT FROM <value>` (standard SQL, NULL-safe on both backends, supported by SQLite since 3.35).** Found in five places (`benutzername_frei`, `email_frei`, `konto_aktualisieren` ×2, `sitzungen_widerrufen_fuer_benutzer`) — `id IS NOT ?` is valid SQLite but a PostgreSQL syntax error once `?` binds to a non-NULL value (PostgreSQL's `IS NOT` only accepts `TRUE`/`FALSE`/`NULL`/`UNKNOWN` on the right); this was the one genuinely silent, would-have-broken-on-first-use incompatibility this analysis found.
- **`UPDATE ... WHERE ... RETURNING ...`** (supported by SQLite since 3.35, identical syntax on PostgreSQL) is now the standard pattern for every single-use token/claim — see "Concurrency" below.

### Concurrency

Every "single-use" or "claim" operation that used to be a Python-level "SELECT, then decide, then UPDATE" is now an atomic, conditional SQL statement, closing races that a single-process SQLite dev setup mostly hid but a multi-connection PostgreSQL production setup would not:

- **Email verification tokens, password-reset tokens** (`email_verifizierung_bestaetigen`, `passwort_reset_einloesen`): one `UPDATE ... WHERE verwendet_am IS NULL RETURNING ...` — of two simultaneous redemption attempts, only one can ever get a non-empty result back. An expired token is still marked used on the first attempt (closes it off from repeated probing; no legitimate functional loss, since it could never have succeeded anyway).
- **2FA login challenge** (`zwei_faktor_challenge_pruefen_und_verbrauchen`): the success path's "mark used" is the same conditional `RETURNING` pattern; the failed-attempt counter is incremented atomically in SQL (`fehlversuche = fehlversuche + 1 ... RETURNING fehlversuche`) rather than read-in-Python-then-written-back, so two concurrent wrong-code attempts can't lose one increment ("lost update").
- **TOTP replay protection** (`zwei_faktor_totp_pruefen`): the write of `letzter_zeitschritt` is now `UPDATE ... WHERE letzter_zeitschritt IS NULL OR letzter_zeitschritt < ?` with a `rowcount` check — two concurrent requests presenting the same valid code can no longer both succeed.
- **Backup-code consumption** (`zwei_faktor_backup_code_pruefen_und_verbrauchen`): the Argon2 candidate search itself is necessarily Python-side (salted hashes can't be matched in SQL), but the actual "mark used" is `UPDATE ... WHERE id = ? AND verwendet_am IS NULL` with a `rowcount` check — only one of two concurrent requests that matched the same row can win.
- **2FA setup start** (`zwei_faktor_setup_starten`): converted from SELECT-then-branch to one atomic `db_backend.upsert_ersetzen` call (see above).
- **Product access grants** (`produkt_zugriff_gewaehren`): already atomic via the unique constraint + `upsert_ignore` — no Python-side check-then-write at all.
- **Verified under real thread concurrency, not just mocks**: `test_dialekt_konsistenz.py`'s `KonkurrenzTests` fire 8 real, concurrent threads (each its own SQLite connection via `speicher._verbindung()`) at the same email-verification token / backup code / 2FA challenge and assert exactly one succeeds.
- **Rate limiting (`ratenbegrenzung.py`) remains a soft, count-based throttle, deliberately not hardened further in this block.** `pruefen()`/`versuch_aufzeichnen()` still do a `COUNT(*)`-over-a-time-window check followed by a separate insert of the new attempt — under true concurrent load this can let a small number of extra attempts through before the next check catches up. This is an accepted, documented limitation: rate limiting is a throttle against automated abuse, not a hard authorization boundary, and hardening it (per-identity row locking or a PostgreSQL advisory lock) was judged disproportionate complexity for a personal-scale app relative to the actual risk. Revisit if real-world abuse patterns ever demand it.
- **Session validity checks / `last_activity_at` updates are not single-use and were left as-is** — two concurrent requests updating the same session's activity timestamp is not a security-relevant race (whichever write lands last is fine).

### Storage-Cleanup-Outbox (delete consistency)

The Block 4 known limitation ("a storage-delete failure can leave an orphaned object") is resolved with a transactional-outbox pattern, new table `storage_cleanup_auftraege` (id, storage_key, art `objekt`/`praefix`, grund, erstellt_am, versuche, letzter_versuch_am, naechster_versuch_am, status `offen`/`erledigt`/`fehlgeschlagen_final`, letzter_fehler, erledigt_am):

```
DB row deleted + cleanup order inserted   (ONE transaction, atomic)
                 │
                 ▼
     Storage deletion attempted immediately (synchronous, best-effort)
        │                                    │
     success                              failure
        │                                    │
  order → "erledigt"              order stays "offen" — retried later
                                   by cleanup_pending_storage_deletions()
```

- The cleanup **order** (the *intent* to delete a specific `storage_key`) is always persisted in the **same DB transaction** as the row deletion that makes the document/account invisible to the user (`speicher._storage_cleanup_auftrag_erstellen`, called from inside the same `with _verbindung() as conn:` block as the `DELETE`) — a storage outage can never make a deleted document/account reappear, because the DB deletion is already committed before any storage call is attempted.
- `speicher._storage_sofort_loeschen_oder_vormerken` then tries the actual deletion synchronously; on success it marks the just-created order `erledigt` immediately (the common case stays a one-step, low-latency delete, same as before this block).
- `speicher.cleanup_pending_storage_deletions(limit=50)` is the (still schedulerless — "keine unnötige Komplexität, kein Scheduler in diesem Block", per the task) maintenance function a future worker/cron/maintenance-task will call periodically: picks up to `limit` open, due (`naechster_versuch_am` elapsed) orders, retries each, and on repeated failure applies exponential backoff (`_naechster_cleanup_versuch`, 5 min base, doubling, capped at 24h) up to `STORAGE_CLEANUP_MAX_VERSUCHE` (10) attempts, after which the order is marked `fehlgeschlagen_final` (visible for future manual/administrative attention, no longer auto-retried) rather than retried forever. No retry loop lives in the Streamlit UI itself.
- **Upload's existing compensation logic (Block 4: storage-write-then-DB-insert, delete-on-DB-failure) now has a fallback for its own failure**: if the compensating storage delete *also* fails (a double fault), a cleanup order is created for that orphaned object instead of silently losing track of it (`dokument_speichern`'s `except` block).
- **Cross-user safety is structural, not enforced by a runtime check**: every cleanup order carries its own, already fully-resolved `storage_key`/prefix, fixed at creation time from the deletion that created it — a cleanup run can never touch another user's key because no order ever references anything other than the exact key/prefix it was created for. Tested explicitly (`test_dialekt_konsistenz.py`'s `test_v_cleanup_von_user_a_loescht_niemals_objekt_von_user_b`).
- **Account deletion (`konto_endgueltig_loeschen`) uses the same pattern** with `art="praefix"` (`users/<id>/`) — the whole account's objects are one cleanup order, not one per file.

### Configuration, testing, and what's still not done

- **Environment variables** (all optional — omitting them keeps today's SQLite + local-file behavior): `CLEVORIQ_DATABASE_BACKEND` (`sqlite` default; `postgresql` now fully schema-/query-compatible), `CLEVORIQ_DATABASE_URL` (`postgresql`-only), `CLEVORIQ_DATABASE_SSLMODE` (default `prefer`, same as libpq; set to `require`/`verify-full` for a real IONOS connection — encrypted DB communication is prepared, not yet exercised), `CLEVORIQ_STORAGE_BACKEND` (`local` default; `s3` requires the `CLEVORIQ_S3_*` variables below), `CLEVORIQ_S3_ENDPOINT`, `CLEVORIQ_S3_REGION`, `CLEVORIQ_S3_BUCKET`, `CLEVORIQ_S3_ACCESS_KEY_ID`, `CLEVORIQ_S3_SECRET_ACCESS_KEY`, and **`CLEVORIQ_TEST_POSTGRES_URL`** (test-only, see below). See `.env.example`.
- **The database connection string is never logged, shown in the UI, or fully embedded in an exception** — `db_backend.DatenbankFehler` messages are always generic technical descriptions; a PostgreSQL connection failure severs the exception chain (`raise ... from None`) specifically because the underlying driver exception can itself contain connection-string fragments, which would otherwise still appear in a full traceback even with a generic top-level message. Same discipline for `storage.StorageFehler` and S3 credentials.
- **`test_postgres_integration.py` — real PostgreSQL integration tests, gated on `CLEVORIQ_TEST_POSTGRES_URL`.** Covers schema creation, migration run twice, registration/login/sessions, email verification, password reset, 2FA + backup codes, product access, document metadata (`public_id`/`storage_key`), chats/chunks, delete cascades, transaction rollback on a constraint violation, and user isolation — against a real, isolated PostgreSQL database (never a production one; every test uses a random `pgtest_<uuid>`-prefixed username so runs never collide or touch pre-existing data; the whole file is additive/non-destructive, never `DROP`/`TRUNCATE`). **Without `CLEVORIQ_TEST_POSTGRES_URL` set, this entire file is skipped, not run against SQLite as a stand-in** — a green test run does NOT mean PostgreSQL has been practically verified. No local PostgreSQL/Docker was available in the environment this block was implemented in, so these tests were written and confirmed to skip cleanly, but have **not actually been run against a real PostgreSQL server** — that remains genuinely unverified until someone runs them against a real (test) instance.
- **What's next (out of scope for this block, per the task).** No IONOS account changes, no server/bucket actually provisioned, no real credentials used anywhere, no customer data migrated, no scheduler/worker wired up to `cleanup_pending_storage_deletions`. When the next block starts: (1) provision IONOS Managed PostgreSQL + a private IONOS Object Storage bucket, (2) actually run `test_postgres_integration.py` against it, (3) point `CLEVORIQ_DATABASE_BACKEND=postgresql`/`CLEVORIQ_STORAGE_BACKEND=s3`/`CLEVORIQ_DATABASE_SSLMODE=require` at the real instances via environment variables only, (4) wire a periodic caller (cron/worker) for `cleanup_pending_storage_deletions`, (5) network/firewall rules, HTTPS, backups, monitoring — none of which are configured or assumed anywhere in this codebase yet.

## Authentication & Security

The auth stack is `auth.py` (Argon2 hashing/validation, no Streamlit/DB imports) + `zwei_faktor_krypto.py` (TOTP/Fernet-encryption/backup-code logic, likewise no Streamlit/DB imports) + `speicher.py` (all persistence: `benutzer`, `email_verifications`, `password_resets`, `sessions`, `security_events`, `zwei_faktor`, `backup_codes`, `zwei_faktor_challenges` tables) + `benutzer.py` (login/register/forgot-password/reset/2FA-challenge UI, session lifecycle) + `konto.py` (profile/password/email-change/export/delete/2FA-management UI) + `ratenbegrenzung.py` (persistent rate limiting) + `sicherheitslog.py` (audit logging) + `email_versand.py` (transactional email, dev or Resend). This is still a single-app, local-SQLite MVP — see "Platform & Product Branding" for the intended future evolution into a shared, cross-product **Clevoriq Account** (SSO across future Clevoriq products is explicitly **not implemented**; nothing here should be mistaken for it). 2FA is **optional per account** (never forced) and, once enabled, is enforced entirely server-side (see "Two-factor authentication (TOTP)" below) — **passkeys/WebAuthn, SMS-based 2FA, and any centralized SSO platform remain deliberately out of scope** and should not be added as part of touching this section.

- **E-mail verification**: `benutzer.benutzer_erstellen` inserts new accounts with `email_verified = 0` explicitly and immediately creates + emails a verification token (`speicher.email_verifizierung_erstellen`, `email_versand.sende_registrierung_verifizierung`). The `benutzer` table's own column default stays `email_verified = 1` (both in `CREATE TABLE` and in the additive `_spalten_ergaenzen` migration) — that default only ever applies to rows *not* inserted through `benutzer_erstellen` (the `MIGRATIONS_BENUTZERNAME` bootstrap account, and any pre-existing row from before this feature), which is exactly what keeps legacy/dev/migration accounts from being locked out. Verification tokens are `secrets.token_urlsafe(32)`, stored only as a SHA-256 hash (`speicher._token_hash`), single-use (`verwendet_am`), expire after `EMAIL_VERIFIZIERUNG_GUELTIGKEIT_STUNDEN` (24h), and creating a new token immediately invalidates any still-valid older one for that user. Changing the account email (`konto.py`) resets `email_verified` to 0 and re-triggers the same flow — the new address must be reconfirmed. A verification link is `{CLEVORIQ_APP_BASE_URL}/?verify_token=...`; `web_app.py` processes `st.query_params["verify_token"]` **before** the login gate (the link is normally opened in a fresh, not-yet-authenticated browser tab), immediately calls `st.query_params.clear()`, and only updates the *current* session's cached `email_verified` flag if it's already logged in as the *same* account the token belongs to (never a different one). Unverified accounts **can log in**, but `web_app.py`'s sidebar/content routing forces them into exactly one restricted area (`benutzer.BEREICH_VERIFIZIERUNG`, plus `BEREICH_KONTO` and logout) — no document upload, no Chat/Analyse/Prüfung. Resending is exposed both from that page and from Konto & Sicherheit through the single shared `benutzer.bestaetigungsmail_anfordern` helper.
- **Password reset ("Passwort vergessen")**: entry point is a button on the login form (`benutzer._login_formular`) switching to `_passwort_vergessen_formular`. The handler (`benutzer._passwort_reset_anfordern`) **always** returns the same fixed string (`benutzer.PASSWORT_RESET_MELDUNG`) regardless of whether the email exists — no account enumeration. `speicher.passwort_reset_anfordern` mirrors the verification-token design (hashed, single-use, `PASSWORT_RESET_GUELTIGKEIT_STUNDEN` = 1h, new token invalidates older ones) and returns `(token, konto_email)` so the caller never needs a second, timing-distinguishable lookup. The link is `{CLEVORIQ_APP_BASE_URL}/?reset_token=...`, processed by `web_app.py` **before** the login gate (`benutzer.reset_passwort_seite`) since this flow is by definition unauthenticated; it never touches `st.session_state`'s active-user key, so a different account's session open in another tab is left alone. On success, `speicher.passwort_reset_einloesen` re-hashes with the existing Argon2 config and calls `sitzungen_widerrufen_fuer_benutzer` with **no exception** — every session of that account is invalidated, forcing a fresh login everywhere.
- **Session model**: `st.session_state` is still the only place the raw per-tab session token lives (no cookie, nothing in the URL beyond the one-time verify/reset tokens which are cleared immediately) — a new browser tab still requires a fresh login, unchanged from before. New: every login/registration also creates a **server-side** row in `sessions` (`speicher.sitzung_erstellen`, token stored only as a hash, never reused — a fresh token every time, which is what prevents session fixation). `benutzer.sitzung_gueltig_pruefen()` **must** run on every `web_app.py` script run while logged in — it validates the token against `sessions` (revoked? past `SITZUNG_MAX_LEBENSDAUER_STUNDEN` = 12h absolute lifetime? past `SITZUNG_INAKTIVITAET_MINUTEN` = 60m sliding inactivity window?) and confirms the row's `user_id` still matches the session dict's own id (a session can never end up validated for a different account). Any failure fully clears `st.session_state` and shows an explanation on the next login screen instead of silently doing nothing. Logout (`benutzer.abmelden`) revokes the row before clearing state; self-service password change revokes every *other* session (`konto.py`, keeps the current one alive); password reset and account deletion revoke/cascade-delete all of them; 2FA disable/rotation re-issue the session outright (`benutzer.sitzung_neu_ausstellen` — revoke-all-then-mint-fresh, same session-fixation care as login). A 2FA login challenge (see below) is a *separate*, lower-privilege server-side record that is never itself upgraded into a session — a session only ever gets created fresh, after the challenge succeeds. **Known Streamlit limitation** (documented, not hidden): there is no HttpOnly/Secure cookie and no way to bind a session to a specific browser at the transport level — this is the most-secure model achievable on top of `st.session_state`, not full protection against network-level session theft. The 2FA UI gating (hiding buttons/forms) is likewise cosmetic only — every 2FA-gated server function (`speicher.zwei_faktor_*`) re-derives and re-checks everything itself and never trusts that a widget wasn't shown.
- **Two-factor authentication (TOTP)**: optional per account, RFC-6238-standard TOTP via `pyotp` — works with any compatible authenticator app (Google/Microsoft Authenticator, Authy, 1Password, Bitwarden, …), no proprietary provider dependency. `zwei_faktor_krypto.py` holds the pure logic (secret generation, `otpauth://` URI building via `pyotp.TOTP.provisioning_uri(issuer_name="Clevoriq")`, ±1-step-tolerant code verification via `pyotp.utils.strings_equal`, backup-code generation); `speicher.py`'s "Zwei-Faktor-Authentifizierung"-section owns persistence and orchestration.
  - **Secret encryption**: a TOTP secret can't be hashed (it must be checked, not just compared), so it's encrypted with `cryptography.fernet.Fernet` (authenticated encryption) and only the ciphertext is stored (`zwei_faktor.secret_verschluesselt` / `pending_secret_verschluesselt`), never plaintext. The key comes **exclusively** from the `CLEVORIQ_2FA_ENCRYPTION_KEY` env var (a Fernet key, e.g. `Fernet.generate_key()`) — never hardcoded, never logged, never echoed in an exception, never auto-generated in production. Missing/invalid key → every encrypt/decrypt call raises `RuntimeError` immediately (fail closed); a user with 2FA already enabled simply cannot complete a TOTP check until the key is restored — there is no plaintext fallback, ever. Each stored secret carries a `secret_key_version`/`pending_key_version` column and `zwei_faktor_krypto.AKTUELLE_SCHLUESSEL_VERSION` + `_umgebungsvariable_fuer_version` are already version-aware (a future `CLEVORIQ_2FA_ENCRYPTION_KEY_V2` would decrypt old-version secrets while new ones use v2) — actual key **rotation** (re-encrypting existing secrets) is schema-ready but not implemented in this block.
  - **Setup flow** (`konto.py`'s "Zwei-Faktor-Authentifizierung" section): current-password confirmation → `speicher.zwei_faktor_setup_starten` creates a **pending** (not yet active) encrypted secret, replacing any previous pending one but never touching an already-active secret → QR code rendered fully **locally** (`qrcode` + `Pillow`, no external service) plus the manual setup key → activation only happens on `zwei_faktor_setup_bestaetigen` with a correct current code, which also mints the one-time backup codes. An abandoned pending secret self-expires after `PENDING_2FA_GUELTIGKEIT_MINUTEN` (15m, lazily reaped in `zwei_faktor_status`) or is discarded immediately via "Abbrechen" (`speicher.zwei_faktor_setup_abbrechen`) — there is no way to end up "half enabled".
  - **Backup codes**: `BACKUP_CODES_ANZAHL` = 10 per activation/regeneration, format `XXXXX-XXXXX` from a 32-symbol alphabet (no `0/O/1/I/L`, ~50 bits entropy each), shown **once** in plaintext right after generation (with a same-session `.txt` download button — nothing persisted server-side) and stored only as an `auth.backup_code_hash` Argon2id hash (the same salted, memory-/CPU-hard `PasswordHasher` config used for passwords — unlike the app's other high-entropy tokens, which are user-facing secrets like passwords rather than server-generated tokens, so `speicher._token_hash`'s plain SHA-256 is deliberately not used here) in `backup_codes`. Because Argon2id hashes are salted, verifying a code (`speicher.zwei_faktor_backup_code_pruefen_und_verbrauchen`) can't do a direct `WHERE code_hash = ?` lookup — it loads that user's still-unused codes (at most `BACKUP_CODES_ANZAHL`) and checks the candidate against each with `auth.backup_code_pruefen` until one matches. Each is single-use (`verwendet_am`); regenerating (`zwei_faktor_backup_codes_neu_erzeugen`) hard-replaces the whole set.
  - **Login challenge**: after a correct password, if 2FA is active, `benutzer._login_versuchen` does **not** create a session — it creates a `zwei_faktor_challenges` row (`speicher.zwei_faktor_challenge_erstellen`, token hashed like a session token, `ZWEI_FAKTOR_CHALLENGE_GUELTIGKEIT_MINUTEN` = 10m expiry) and `authentifizierung_anzeigen()` renders the challenge screen with top priority over any other login-page mode, so a user can't navigate away mid-challenge without explicitly cancelling. `speicher.zwei_faktor_challenge_pruefen_und_verbrauchen` always re-derives `user_id` from the challenge row itself (never from a caller-supplied value), is single-use, and self-terminates after `ZWEI_FAKTOR_CHALLENGE_MAX_FEHLVERSUCHE` (5) wrong codes — a terminated or expired challenge forces a fresh password login, no exceptions. A full session is only minted *after* the challenge succeeds, with a brand-new token (same anti-fixation care as any login).
  - **Replay protection**: `zwei_faktor.letzter_zeitschritt` records the last TOTP time-step accepted for a user; `zwei_faktor_krypto.totp_code_pruefen` rejects a step ≤ that value even if otherwise valid, so an intercepted code can't be reused within its own validity window, while any later step (including normal small clock drift) still works.
  - **Re-authentication gate for sensitive changes**: 2FA disable, 2FA re-setup/rotation, backup-code regeneration, an active email/username change, and account deletion all require the current password **and**, if 2FA is active, a second-factor code — `konto._zweiter_faktor_bestaetigen` (auto-detects TOTP-vs-backup-code by format so a single input field suffices inside `st.form`) is the one shared implementation. Backup-code regeneration specifically requires TOTP only (not a backup code) — you can't indefinitely mint fresh backup codes using only a backup code. There is **no account-recovery bypass**: losing both the authenticator and all backup codes means no self-service reset is offered (the UI says so plainly) — that is intentionally left for a future, separately designed recovery flow rather than a shortcut that would undermine 2FA's value.
  - **Interplay with existing flows**: password reset (`speicher.passwort_reset_einloesen`) never touches the `zwei_faktor`/`backup_codes` tables — 2FA survives a reset, and the next login still needs the new password *and* a valid second factor. Deleting an account cascades away all three 2FA tables via `ON DELETE CASCADE`.
  - **Rate limiting additions** (`ratenbegrenzung._LIMITS`, all 5 attempts/15 min except the two 60-min ones, same escalation model as the rest of the file): `totp_verify`/`backup_code_verify` (wrong codes during a login challenge, keyed by `user:<id>` so the count survives across multiple fresh challenges rather than resetting each time), `2fa_setup_verify` (wrong setup/rotation confirmation code), `2fa_disable` (wrong second factor while disabling, rotating, changing email, or deleting the account — one shared bucket, same threat model), `backup_codes_regenerate` (5 attempts/60 min).
- **Rate limiting**: persistent, not an in-memory dict — every attempt is written to `security_events` (`ratenbegrenzung.versuch_aufzeichnen`) and `ratenbegrenzung.pruefen(aktion, identitaet)` counts a sliding window over that table, so it survives app restarts. Keyed by the **normalized identity** (lowercased email/username, or `user:<id>` for already-authenticated 2FA actions) only — deliberately identical handling regardless of whether an account actually exists, so no path lets an attacker distinguish "wrong password" from "no such account". Current limits (`ratenbegrenzung._LIMITS`): login 5 failed/15 min; register, password-reset-request, resend-verification 5 (or 3 for resend)/15–60 min regardless of outcome; invalid email-verification-token attempts 10/15 min; 2FA limits as listed above. A repeated lockout within a rolling 24h window doubles the next lockout (capped at 4h) via `_eskalierte_sperre_minuten`, deduplicated so retrying *during* an active lockout doesn't itself inflate the escalation. Resending the verification email additionally has its own flat 60s cooldown (`RESEND_COOLDOWN_SEKUNDEN`) on top of the broader limit. Client IP (`ratenbegrenzung.client_ip`, best-effort `X-Forwarded-For` via `st.context.headers`) is logged for audit purposes only — it is never load-bearing for a rate-limit decision, since Streamlit gives no reliable, proxy-safe way to establish it.
- **Security/audit logging** (`sicherheitslog.py`, writing to the same `security_events` table): login success/failure, registration, rate-limit trips, password changed/reset, email changed/verified, verification resent, logout, session invalidation, account deletion, plus 2FA setup started/enabled/setup-failed/challenge-failed/login-success, backup-code used/regenerated, 2FA disabled/secret-rotated/rate-limited. Never logs passwords, raw tokens, TOTP secrets, TOTP codes, backup codes, encryption keys, API keys, or document contents; only the normalized identity string and (for authenticated events) the internal user id. Nothing consumes this yet beyond the DB itself — a later step could stream/export it to real monitoring without touching any call site, since `speicher.sicherheitsereignis_speichern` is the single write path.
- **Resend integration** (`email_versand.py`): `_ResendAnbieter` is a plain `urllib` HTTPS POST to `api.resend.com` — no new dependency. Selected via `CLEVORIQ_EMAIL_PROVIDER=resend` (falls back to the historical `AVENLOQ_EMAIL_PROVIDER` name if that's what's set); anything else (including unset) stays on `_EntwicklungsAnbieter`, the default dev/test provider that never makes a network call, only logs to stdout and to the in-process `email_versand.GESENDETE_ENTWICKLUNGS_MAILS` list — this is what keeps `test_auth_security.py` and any local dev session from ever sending real mail. If `resend` is selected but `RESEND_API_KEY` or `CLEVORIQ_EMAIL_FROM` is missing, the provider raises immediately with a message naming only the missing *variable*, never a secret value — it never pretends a send succeeded. Domain verification at Resend is entirely out of band and never simulated in code.
- **Environment variables** (all optional in dev — omitting them just keeps the dev email provider active):
  - `RESEND_API_KEY` — Resend secret API key. Never log it, never put it in an exception message, never commit it.
  - `CLEVORIQ_EMAIL_FROM` — sender, e.g. `Clevoriq <noreply@notify.clevoriq.de>` (must be a Resend-verified sender domain in production).
  - `CLEVORIQ_EMAIL_REPLY_TO` — optional, e.g. `info@clevoriq.de`.
  - `CLEVORIQ_EMAIL_PROVIDER` — `resend` to go live; anything else/unset stays on the dev provider. (`AVENLOQ_EMAIL_PROVIDER` still works as a deprecated fallback name.)
  - `CLEVORIQ_APP_BASE_URL` — base URL used to build verification/reset links (default `http://localhost:8501` for local dev; **must** be set to the real deployed URL in any non-local environment).
  - `CLEVORIQ_2FA_ENCRYPTION_KEY` — Fernet key (`cryptography.fernet.Fernet.generate_key()`) encrypting TOTP secrets at rest. **Required** before any user can set up or use 2FA; without it, 2FA setup/verification fails closed with a clear error (see "Two-factor authentication" above) rather than falling back to anything insecure. Treat exactly like `RESEND_API_KEY`: never log it, never commit it, never lose it while any account has 2FA enabled (there is no recovery from a lost key other than restoring it). `CLEVORIQ_2FA_ENCRYPTION_KEY_V2` (etc.) is the prepared-but-unused naming convention for a future key rotation.
- **No secrets committed, ever** — this applies to the values of all of the above, and to anything else resembling a credential; `.gitignore` already excludes `app_daten/` and `.streamlit/secrets.toml`, plus `.env`/`.env.*` (any local secrets file). Never hardcode a real key/token anywhere in this repo, including in tests — `test_auth_security.py`'s `_TEST_2FA_SCHLUESSEL` is a throwaway key generated solely for that test run, not a real credential.

## API cost-awareness rules

The codebase has several deliberate patterns to keep OpenAI usage cheap; preserve them when extending the app:

- **Batch embeddings, never loop per-chunk.** A newly uploaded document's chunks are embedded in one call (`retrieval.embeddings_batch_erstellen`), not one call per chunk.
- **Cap chunks per document, and scale the cap down as document count grows.** Chat uses 4 chunks/doc for a single active document, else `max(2, 8 // anzahl_dokumente)`; Analyse & Vergleich uses 8/doc; a single Dokument-prüfen category uses 6/doc; `kompletter_check` uses 12/doc but folds all categories into one call (see below) rather than multiplying calls.
- **Prefer one combined model call over N smaller ones.** `pruefung.kompletter_check` runs all six categories through a single combined search query and a single Responses API call instead of six independent (6x cost) calls — follow this pattern for any new "run everything" action.
- **Keep answers terse by instruction, not just for readability.** `ki_analyse.KUERZE_HINWEIS` (bullets/tables over prose, no filler) caps output tokens on every AI-analysis feature; `pdf_logik.frage_beantworten`'s system prompt follows the same idea for Chat.
- **Never spend a model call on something a heuristic can do.** Chat titles are derived with a plain string function (`speicher._kurztitel_erzeugen`), not an API call.
- **Dedup uploads by content hash before parsing/embedding** (`speicher.dokument_nach_hash`) so re-uploading an unchanged file never re-spends embedding cost.
- When adding a new AI-analysis feature, build it on `ki_analyse.py` (fixed/topical search query + capped per-document chunk count + one model call) rather than inventing a new retrieval/prompt/API pattern.
